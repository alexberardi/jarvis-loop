# The planning stages: how they are built

2026-10-15 · phase 7 (`docs/phases/07-planning.md`). The user asked to start the planning stages
designed on 2026-10-14 (DESIGN.md, "Planning, before the loop"). Choices made in the spec:

- **Briefs and blueprints are pages on loopd's board** (`/board/plans/{id}`), not Claude Docs
  pages. Agents in the loop run with no MCP servers (prompt caching, 2026-10-15) and the runner is
  plain Go with no Docs connector, so nothing in the loop could write a Docs page. The board is
  already on the user's phone (LAN, read-only token), and the conversation itself is the Slack
  thread, so comments are replies there. The final copy still goes into the target repo
  (`docs/plans/<plan>.md`), committed by the plan's first item. Revisit when loopd moves behind
  Cloudflare Access (rollout 9) if the board should be reachable away from home.
- **One agent per message, resuming one session per persona** (`claude -p --resume`), in a stable
  directory per plan, so the thread is never replayed and the prefix stays cached. Messages that
  arrive during a turn join the next turn.
- **Approvals bind to the document's sha256**, the way merge approvals bind to the head sha, so an
  Approve button can't approve a version the user hasn't seen.
- **Dependencies are a general item feature** (`depends_on`), usable by hand (`--after`) and built
  first, since plans need them and they help without plans too. `qa` doesn't satisfy a dependency.
- **Planning turns share the active-agents limit** with items; a waiting user beats a queued item of
  the same priority.
- **Built through the loop as five items**, each held at land (they change the pipeline, store,
  API or the approver check).
