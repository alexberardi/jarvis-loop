# Dropping an item

2026-10-15 · item #13. The user needs to close items they can't or won't land (#6 device-kasa, #7
device-lifx: no hardware to verify on). What was chosen, each enforced by a test or a scenario
(`scenarios/31-drop.json`).

## The action

- **User only.** `POST /items/{id}/drop` takes the user token; a runner token gets 403
  (`TestAuth`, `TestDropRoute`). In Slack, only the approver: the **Drop** button and `/loop drop`
  go through the same approver check as Approve, and someone else's press or command is refused and
  recorded (`refused`) on the item. A runner or an agent can never close work the user asked for.
- **From any open stage** (triage, build, review, land, needs_you, held) to `closed`;
  `done` and `closed` are refused with `wrong_stage` (`pipeline.ApplyDrop`, `TestApplyDrop`). The
  item's open question and return stage are cleared. The event is `dropped`, with
  `reason: "dropped by the user"` and the user's words (the button's are "Drop button").
- **Where:** a Drop button (with Slack's confirm dialog) on the held message and on the needs-you
  message, the two places the loop asks the user something; `/loop drop N [why]` for any other
  stage; `loop drop <id> [--words TEXT]` on the CLI. A pending reply approval on the item is
  cancelled, so it cannot apply after the drop.
- **The thread gets one line:** "Dropped by you: '…'. Closed; the runner closes <PR> (the branch
  stays)." The later `pr_closed` event posts nothing.

## A running agent

The drop ends the item's live lease in the same transaction, the way overtime does
(`end_reason = "dropped"`, the lease, runner and agent go in the event's data). The runner learns
it from its next heartbeat (`stop`), kills the agent and treats it as stopped (a build's work is
saved to its branch as on any stop); its report finds no lease (`no_lease`) and cannot move the
closed item (`TestDropEndsTheLiveLease`).

A land run, which has no agent, cannot wait for its heartbeat: it polls GitHub every 30 s and the
heartbeat comes every 60 s, so CI passing in between would merge a dropped item's PR, and a merge
cannot be undone. So land reads the item's stage from loopd before every pass of the gates (it
already re-reads the item there) and stops, without merging or reporting, when the item is no
longer in land (`TestDropDuringLandDoesNotMerge`, scenario `drop-during-land`). The PR is then
closed by the drop sweep like any other. What is left is the few seconds between that read and
the merge call (one `gh pr view` and a git fetch).

## The PR: closed by the runner, once, idempotent

- **The runner closes it, not loopd:** loopd holds no GitHub credential; the runner has the user's
  own gh login (`2026-10-15-runner-pushes.md`). Each runner, on every poll (a goroutine next to the
  claim slots in `Run`; the sandbox's `runner` step does it before claiming), asks loopd for
  `GET /items?pr_to_close=1`: closed items with a PR, a `dropped` event and no `pr_closed` event.
  It only handles repos in its own config.
- **Read first, then close:** `gh pr view --json state`; only an `OPEN` PR gets
  `gh pr close N --repo slug --comment "Dropped by the owner"`. **No `--delete-branch`**: the
  branch stays, so the work can be picked up again by hand.
- **Idempotent:** a PR already `CLOSED` or `MERGED` (#6's and #7's were closed by hand) is not
  touched; the runner only records `pr_closed` with `state: already_closed` / `already_merged`.
  `pr_closed` is a runner event like `main_ci`: no lease needed, refused unless the item is closed,
  dropped and has a PR, and recorded once (`already_recorded` on a second; two runners racing is
  harmless). A gh failure leaves the item on the list for the next poll.

## Not done

- Typed thread replies ("drop") are not a drop; only the button and the command are, so a
  conversational reply can never close work.
- The guard does not newly deny `gh pr close` to agents: they hold no GitHub credential.
