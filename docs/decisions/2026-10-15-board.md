# The swim-lane board is a LAN web page with its own token kind

2026-10-15 · item #14

**Decision.** The board the user looks at from a phone is a web page served by loopd at `GET /board`,
not the Slack Home tab. It is read-only: approving, answering and the active-agents control stay in
Slack (approvals bound to the user's Slack ID) and on the status page.

- **Columns.** Planning (empty until the planning stages exist) · Triage (`intake`, `triage`) ·
  Build (`ready`, `build`) · Review (`review (queued)`, `review`, `land (queued)`, `land`) ·
  Needs you (`needs-you`, showing the question) · Approval (`held`, showing the hold reason) · QA
  (empty until a QA stage exists) · Done (`done` items whose last change is at most 14 days old;
  `closed` ones only with `?closed=1`). Land sits under Review: it is the loop merging what review
  approved, with no agent and nothing for the user to do; a land that needs the user is `held` and
  shows under Approval. Where a column holds more than one display stage, the card names it.
- **Cards.** #id, title, repo short name, priority, age, the claiming runner/agent, the PR link,
  the Slack thread link, and the question or hold reason. A card opens `/board/items/{id}`: the
  item's fields, its evidence (PNG, JPEG, GIF and WebP inline, every other file a download with
  `Content-Disposition: attachment`; SVG is a download, since it can carry script) and its events.
- **No JavaScript** (amended 2026-10-16: one same-origin script refreshes the "Working now"
  section, [working-now](2026-10-16-working-now.md)). html/template with embedded templates, no external JS or CSS. The 30-second
  refresh is `<meta http-equiv="refresh">`, the closed toggle a link. The CSP is
  `default-src 'none'; style-src 'unsafe-inline'; img-src 'self'; form-action 'none'; frame-ancestors 'none'`.
  On a phone the columns scroll sideways (scroll-snap) with a 16px gutter, and
  `prefers-color-scheme: dark` switches to the dark palette.
- **Token kind `board`.** A new kind in the tokens file. The API refuses it on every route, reads
  included (403), and so does the status page. The board accepts `board` and `user` tokens: the
  user's token can already do everything the board shows. Runner tokens get 403.
- **Sign-in.** `GET /board?t=<token>` (any board route) checks the token, sets
  `loop_board=<token>; Path=/board; HttpOnly; SameSite=Strict; Max-Age=30 days` (plus `Secure` when
  the request came over TLS) and answers 303 to the same address without `t`. Later requests sign in
  with the cookie alone. A wrong token gets 401 with a short text, a runner token 403, and neither
  sets a cookie. Bearer and basic-auth headers are not accepted on the board.
- **Second listener.** `loopd --board-addr <host:port>` (e.g. `0.0.0.0:7790`) starts a second HTTP
  server whose handler serves only the three board routes (404 elsewhere, 405 for anything but GET).
  The API stays on `--addr` (127.0.0.1). A non-loopback `--board-addr` does not need `--lan`: the
  flag is the opt-in, and what it exposes is read-only. The main listener serves `/board` too. Both
  servers stop together, and either one failing stops loopd.
  **Dropped 2026-10-23 (#550):** `--board-addr` is gone with loopd's move to fly.io, where
  everything arrives on the one TLS port and the board token's route rules are what separate the
  board from the API ([decision](2026-10-23-loopd-on-fly.md)). The sign-in,
  the cookie and the refusals above are unchanged, and `loopd.BoardHandler` stays for the loop's
  harness and for anyone putting the board on a listener of its own.
- **Slack links.** loopd stores each item's channel and ts but not the workspace, so
  `--slack-workspace https://<team>.slack.com` gives the permalink base
  (`<workspace>/archives/<channel>/p<ts without the dot>`); without it the cards have no thread link.

**Why the token may appear in a URL once.** This supersedes part of
[2026-10-14-web-page-auth](2026-10-14-web-page-auth.md), which kept tokens out of URLs. Basic auth
does not suit a phone home-screen link, and a link with the token is what the user can open from a
note or a QR code. The exposure is bounded: the token is the `board` kind, which reads the board and
nothing else; the 303 strips it from the address bar, so it is not in the page's URL, bookmarks or
the refresh; `Referrer-Policy: no-referrer` keeps it out of any `Referer`; loopd's request log never
records the query (`api.Logged` logs the path only); and `Cache-Control: no-store` keeps the pages out
of caches. It stays in the browser history entry of that one request, which is why the user token
should not be used this way, though it works. The cookie is `HttpOnly` (no script reads it; the page
has none anyway) and `SameSite=Strict` (no other site's link or form sends it), and the board takes
no action, so there is no cross-site request to forge.

**Consequences.** To revoke a phone, remove its board token from the tokens file and restart loopd;
its cookie then gets 401. The status page at `/` keeps basic auth with the user token. When the
Cloudflare Tunnel arrives (rollout 9), Cloudflare Access sits in front of the board as well; until
then, plain HTTP on the LAN means anyone on the LAN who can sniff traffic can read the cookie.
