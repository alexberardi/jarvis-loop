# Land has its own lane in the runner

2026-10-16 · item #24. **Seen:** item #21 was approved in Slack at 08:36 and sat in "land (queued)"
while #22's build agent held the runner's only slot (`slots: 1`): the merge waited for a whole
build. Land runs no agent (the gates, one `gh pr merge`, a background watch of main's CI), so it
should not wait for an agent slot. What was chosen, each covered by a test or a scenario:

- **Two lanes in `Runner.Run`.** `Runner.Lanes` splits the config's `stages`: the agent lane (every
  stage but land) runs in `slots` goroutines as before; the land lane (only when `stages` has
  `land`) is **one** more goroutine that claims with `stages: ["land"]` only, so the runner lands one
  item at a time, as loopd's land limit (1) already says. Both lanes share the claim/poll loop
  (`ClaimAndRunIn`). `TestLandRunsWhileAnAgentHoldsTheSlot`: with `slots: 1` held by a hanging build,
  an approved item lands and the build keeps its lease.
- **No empty stages list.** loopd reads an empty `stages` as "any stage", so a land-only runner
  starts no agent lane at all (`Lanes` returns nil, not `[]`): `TestLanes`,
  `TestLandOnlyRunnerClaimsOnlyLand`. A `["plan", "land"]` runner keeps a plan-only agent lane (the
  client already turns `plan` into kinds).
- **A paused runner still lands.** The runner pauses (stops claiming) when auto mode is unavailable;
  that is about the agent's classifier, and land runs no agent. So a paused `ClaimAndRunIn` claims
  only land, and the land lane goes on: `TestPausedRunnerStillLands`. `/loop stop` is different:
  loopd refuses every claim while stopped, land's included, as before.
- **`--once`** (`ClaimAndRun`) still claims once in every configured stage.
- **loopd is unchanged**, its per-stage limits included.

## Known limit: loopd's active-agents cap counts land

loopd's `active_agents` (`pipeline.ChooseWork` and `Choose`: `len(live) >= ActiveAgents`) counts
every live lease, land's too. With the default (4) and `slots: 1` that leaves room. But with
`active_agents` set to the runner's slots (say 1), loopd still refuses the land claim while the build
lease is live, and the delay comes back. The ask was to keep loopd's limits, so this stays; the
follow-up, if it bites, is to leave land leases out of that count (it is a change to loopd's claim
rules, which the hold rules send to the user).

## The harness

The sandbox drives the runner one poll at a time (`Stack.Poll`). Poll now keeps to the lanes as
`Run` does: with every agent slot working it claims only land, with the land lane working only agent
stages, with both nothing; with room in both it claims once in every stage (in `Run` each lane would
claim; the scenario sees the one loopd hands out first). `scenarios/44-land-own-lane.json`: a P1
build hangs in the only slot, an approved item is claimed for land next to it, waits for CI and
merges; a second build item waits for the slot; `/loop stop` ends the build.
