# The land script (phase 6)

2026-10-15 · phase 6 (`docs/phases/06-land.md`). Where the spec left room or turned out wrong
against the code, and what was chosen. Each is enforced by a test or a scenario unless it says
otherwise. **Not yet run against real GitHub**: the rollout on the dev box is the main session's,
after the user's "merge it".

## Shape: pure gates, an executor that re-derives everything

- `runner.Decide(LandFacts) Decision` is the gate order as a pure function (table test
  `TestDecide`, one row per gate and one per "an earlier gate wins"). It returns advance (an
  outcome and its fields), wait, conflict or merge.
- The executor (`land_run.go`) builds `LandFacts` afresh on **every pass**: the item and its
  history from loopd (`GET /items/{id}`), the PR from GitHub, the changed paths from the mirror's
  git, the hold rules from loopd's control. Nothing is carried over between passes but the wait's
  start and the count of refused merges.
- A runner claims `land` only with `"land"` in its config `stages` (default still triage, build,
  review). `loop-runner --dry-run` refuses a config with `land`.

## Gate details

1. **The PR.** Besides open, not draft and the configured base, the PR's head branch must be the
   item's `loop/` branch: land never merges a PR that is not the one the runner opened. `MERGED`
   (by hand) is recorded as `merged` with GitHub's merge commit and `merged_outside: true`; loopd's
   approval check still applies to it, so a held item merged by hand without an approval is refused
   by loopd and goes to the user (`failed`, "merged on GitHub … loopd refused"). `CLOSED`, draft,
   wrong base or branch: `failed` (needs-you), not `back_to_build`: none of them is the builder's
   to fix.
2. **Review head.** The `head_sha` of the item's last `advanced/approved` event (the review's, not
   the user's `approved`). No review approval at all also goes `back_to_review`.
3. **Changed paths** come from `git diff --name-status -M origin/<base>...<head>` in the runner's
   mirror after a fetch (`Git.DiffPaths`). A head missing from the mirror (a branch GitHub deleted
   after a hand merge) is fetched from `refs/pull/<n>/head` first. No changed files: `failed`
   (loopd requires paths for every land outcome but `failed`).
4. **CI** is read from `statusCheckRollup` in the same `gh pr view` call, not from `gh pr checks`:
   one consistent read with the head it belongs to, and `gh pr checks` exits 8 while checks are
   pending (its help) and errors out when none are reported. Bucketing follows gh: `SUCCESS`/`NEUTRAL` pass, `SKIPPED` is
   `skipping` (counts as passed), `CANCELLED` cancel, anything else completed is a failure
   (including conclusions gh may add later); a status context's `ERROR` fails. A re-run replaces
   the earlier run of the same check (`workflow/name`, latest `startedAt`). The failing check
   names and links go in `back_to_build`'s **`reason`** (loopd requires `reason`, not `notes`).
5. **Evidence:** at least one evidence file attached under the lease of the item's last
   `pr_opened` event (the `lease_id` on loopd's evidence rows), and the PR body must contain the
   runner's `### Verification` heading **and end with its trailer line**: the runner appends the
   footer after the agent's text, so an agent quoting the footer in its own body does not pass for
   it, and an edit after the runner's is noticed.
6. **Hold** is checked by the runner **before** the merge, with the same rules loopd uses: the item
   is held if loopd's risk is `hold`, or if loopd's hold rules (`GET /control`) match the paths
   land computed. loopd's own check at `merged` happens after GitHub has merged, so it cannot be
   the one that stops a merge. Land's `hold` reason is always "on the hold list", so repeated holds
   do not pile up reasons on the item.
7. **Mergeable:** `MERGEABLE` merges (behind or not); `UNKNOWN` (or none) waits like CI.

## Waiting

- One wait budget per claim, for CI and for GitHub's mergeability: `land_ci_wait` (config, a Go
  duration, default `30m`), capped at loopd's per-run cap minus 2 minutes so a wait ends as land's
  own `failed` ("CI (…) still pending after 30m"), never as a run overtime.
- Poll every 30 s; heartbeat every 60 s (as agent runs do). A heartbeat that says stop, or a lease
  that is gone, ends the claim without a report: the item stays in land.
- After 10 minutes the runner records a `land_waiting` event once (a runner event kind with the
  lease, like `guard_refused`). The bot posts nothing for it; while it is the item's latest event
  the parent's stage line reads "Stage *land, waiting for CI (check) since 13:00 UTC*".

## Conflicts

The spec's "resolve by taking both sides only if git resolves it" was read as:

1. Merge `origin/<base>` into the PR's head in a scratch worktree of the mirror (`git merge
   --no-ff`, the runner's identity, hooks off). Clean: push.
2. Conflicts, and any conflicted path outside `docs/`: `back_to_build` naming the paths. No
   conflicted path at all but a failed merge: `back_to_build` with git's message.
3. Conflicts only under `docs/`: abort and merge again with git's **union** driver for `docs/**`,
   given as `-c core.attributesFile=<work>/land-union.attributes`. Git keeps both sides' lines;
   no `-X ours/theirs`. Nothing is written into the mirror's config or the branch's
   `.gitattributes`.

The merge goes to the item's branch only forward (the mirror's branch must be absent or an
ancestor), then out through the runner's existing push (only `loop/…`, never forced), and the item
goes `back_to_review` with the new head and its paths: the merge is a new commit nobody reviewed.

## Merge

`gh pr merge <n> --repo <slug> --squash --delete-branch --match-head-commit <head>`, with `<head>`
the full sha the gates checked (`GH.Merge` refuses anything else before calling gh; `TestGHLand`
pins the argv and that `--auto`/`--admin` never appear). gh runs in `<work_root>/gh`, a directory
that is no checkout, so it never touches a local repository. After gh returns, the PR is read
back: anything but `MERGED` with a merge commit (a merge queue or auto-merge took it) is `failed`
with that said loudly, since nothing the gates checked binds a later merge.

## After the merge: main's CI

- The spec said to heartbeat the item's lease while watching; but loopd ends the lease when
  `merged` is recorded (the item is done). So the watch runs **in the background, outside any
  lease**: the runner's slot is free for other work meanwhile, `Runner.Run` (and `Wait`, used by
  `--once`) waits for it at shutdown. A shutdown mid-watch records nothing (logged); not retried.
- `gh run list --commit <merge> --json name,workflowName,status,conclusion,url`. No runs yet, or
  any not completed: keep polling until `land_main_wait` (default `30m`), then `timeout`.
  Every run `success`/`neutral`/`skipped`: green; else red with the failing runs' names.
- **Red:** the P1 item is filed **first** (`POST /items`, source `finding`, the repo's slug, title
  "main red after #<pr>: <failing>", the ask naming the merge, the item and the run URLs), so the
  `main_ci` event can carry `p1_item` and the item's thread line links it.
- **`main_ci` endpoint:** `POST /items/{id}/events` kind `main_ci`, runner token; the item must be
  done, its last `merged` event must be this runner's (that is the proof of "merged by a run of
  this runner", since there is no lease left), and only once per item. Data is a whitelist:
  `result` (green/red/timeout), `urls`, `failing`, `merge_sha`, `p1_item`.
- **The mention:** the bot @mentions the approver in the thread of any P1 item whose source is not
  `user` ("P1, filed by the loop: …"). The user's own P1s ping nobody.
- The digest has a "Main CI not green" section (red and timeout).

## Per-repo hold rules

- `HoldRule.repo` (owner/name). A rule with a repo applies to that repo's items; one without, to
  every repo. An item whose repo is unknown gets **every** rule (holding more is the safe
  direction); an item whose repo is a bare name (a runner config key, before `pr_opened` reports
  the slug) matches a rule's repo by its name part. `pr_opened` matches on the repo it reports.
- A rule is identified by (repo, name, glob): a name repeats within a repo for several globs
  (`land` covers three files) and across repos (`ci`, `deleted-test`).
- jarvis-loop's defaults are the spec's, plus **`tokens`**: `internal/slack/env.go` (Slack
  tokens), `internal/runner/config.go` (the runner's loopd token) and `internal/runner/client.go`
  (sends it), for "token handling" in jarvis-loop's CLAUDE.md merge rule. loopd's own tokens are
  under `internal/api/**` already.
- `slack-approver` is `internal/slack/approve*.go`: `Approver`, `IsApprover`, `ClassifyReply`, the
  refusal, reply approvals and their window, the button approval and Cancel moved there from
  `api.go`, `text.go` and `bot.go` (a move, no behaviour change; the existing tests pass as they
  were). **Limit:** the call sites that decide *when* to check (`onMessage`, `onActions`,
  `runCommand`) stay in `bot.go` and `commands.go`, which the rule does not cover (item #2 changed
  them and must not be held). A change that drops an `IsApprover` call is caught by review and by
  scenarios 4 and 22, not by the path rule.
- Migration 0004 tags every rule a user had set without a repo with jarvis-server's slug (the
  built-in defaults, stored as `''`, are untouched and now carry their repos).

## Harness

- The sandbox points the built-in rules at its scratch repos (`sandbox.SandboxHoldRules`, set with
  `Store.SetDefaultHoldRules`, an in-memory default like `SetRepos`: no control event, which
  scenario 4 checks there is none of).
- The fake GitHub: checks per (repo, head) set by a `ci` step; mergeability from `git merge-tree
  --write-tree` against the base; `Merge` refuses a closed PR, a moved head, a conflict or a
  scripted refusal, else writes the squash commit (`<title> (#n)`) with `commit-tree`, moves main
  and deletes the branch; workflow runs on merge commits from a `ci` step's `main`. Steps `push`
  (someone else's commit on an item's branch or on main) and `github` (`refuse_merges`,
  `merge_by_hand`). Main is checked against where the fake last put it (start, merge, scripted
  push) instead of "never moves".
- New expectations: `agent_runs` (stage → run dirs; land has none), PR `state` and `merge_calls`,
  `remote.main` (main is that item's squash commit).
- Scenario 17 approves by **reply**, to show the 2-minute window: the button applies at once
  (unchanged, `TestButtonApprovalIsImmediate`).
- Scenario 21 is two files (`conflict-code`, `conflict-docs`); added beyond the spec's list:
  `ci-timeout` (no checks is a wait, not a pass), `merge-refused` (the retry and the second
  refusal), `merged-by-hand`.

## Not verified

- Anything against real GitHub: the `statusCheckRollup`, `mergeCommit` and `gh run list` JSON was
  written by hand from gh's documented shapes (field names checked against the installed gh
  2.102.0's `--json` lists), not recorded from github.com; `--delete-branch` with `--repo` deleting
  only the remote branch; `--match-head-commit`'s refusal text; what gh does on a repo with a merge
  queue (the read-back catches it, untested).
- The union merge on real `docs/` conflicts (only an add/add of one file in the harness).
- The rollout: `land` in the dev box runner's stages, the `loop-runner.service` unit.
