# QA proofs: each item in qa proves itself; only manual checks reach the user

2026-10-18 · item #194. **The user's goal (2026-10-17):** the QA column holds only what truly needs
the user's eyes; everything checkable is checked by the loop, including retroactively for the items
already in qa. That day 12 items waited in qa, and items depending on them idled slots (#61, #63 and
#121 behind #94's QA). Extends the QA lane ([2026-10-15-qa.md](2026-10-15-qa.md)) and QA after deploy
([2026-10-16-qa-after-deploy.md](2026-10-16-qa-after-deploy.md)). Each point is enforced by a test
(`internal/pipeline/proof_test.go`, `internal/store/proof_test.go`, `internal/store/proof_e2e_test.go`,
`internal/runner/proof_test.go`, `TestProofRoutes`, the board goldens) or a scenario
(`scenarios/66-…` to `71-…`, `73-proof-e2e-regression`).

## The proof

- **A proof is a list of checks** (`pipeline.Proof`, on the item as JSON, migration
  `0025_proofs.sql`; the usage migration that took the same number is `0026_usage.sql`), at most 10, each one of five kinds:

  | kind | fields | who checks it | how |
  |---|---|---|---|
  | `usage` | `event`, optional `actor`, `match` | loopd | an event of that kind in loopd's own log after the item's merge (or its deploy), by one of `actor`, whose data has one of each `match` key's values |
  | `command` | `run` | the runner | one shell line, fenced, in a fresh checkout of the repo's main; exit 0 passes |
  | `pi` | `run` | nothing yet | waits: the test Pi device (`feat/pi-device`) is not on main |
  | `e2e` | `tests` | loopd, from a regression run | waits for the next regression run that runs its specs or flows (#195, below) |
  | `manual` | `look` | the user | one line: what to look at |

  Examples: #94 `{"kind":"usage","event":"claimed","actor":["runner:mbp","runner:mini"]}`; #131
  `{"kind":"usage","event":"rebuild","match":{"source":["needs_you"]}}`.
- **The builder states it**: `proof` in build's `ready_for_pr` result (the brief's contract and
  `skills/build`). The runner checks it strictly (`pipeline.ParseProof`: known kinds, each with only
  its own fields; a bad proof refuses the result with the reason, and the agent gets its one retry),
  sends it with `pr_opened`, and puts it in the PR body's Verification footer, so **review sees what
  the loop will check**. A rebuild that states none keeps the one it had.
- **Usage is a pattern, not a query.** The vocabulary is closed in shape: an event kind
  (`^[a-z][a-z0-9_.]*$`), an actor list and equality on top-level data fields. No SQL, no regexps;
  loopd evaluates it in Go over `events`. Events up to the item's newest merge or deploy event do
  not count: before that the change was not in use (the item's own triage claim is not use). Nor
  do the item's own proof records (`proof_set`, `proof_checked`): a proof cannot pass on its own
  checks. Those of other items still count.

## Checking it

- **Due** (`pipeline.ProofDue`): in qa, not waiting for a deploy, an automatic check (usage or
  command) not passed, and never checked or not for **30 minutes** (`ProofRecheck`). loopd lists them
  (`GET /items?proof_due=1`).
- **The runner that works on main checks them**: the one with the land lane (as it watches the held
  PRs), every minute (`ProofEvery`; loopd says what is due). Mac runners, which take only their own
  resources, do not. For each due item of a repo it has, it runs the **command checks not yet
  passed**, fenced exactly as verify steps are (the same fence, masks and caches; env `LOOP_ITEM`,
  `LOOP_REPO`, `LOOP_BASE`, `LOOP_MERGE_SHA`), with a 10-minute cap, in a detached checkout of
  `origin/<base>` that it removes after. The evidence is how it ended and the tail of its output
  (1,400 characters, the last line first). It reports **`proof_checked`** (`POST /items/{id}/events`,
  data `{results: [{check, state, evidence}]}`, runner auth, no lease, like `deployed`). A command it
  cannot run (no fence, no checkout) is left out and stays pending: the runner's trouble is not the
  change's. Never the user's machines, never the repo checkouts in `~/jarvis`.
- **loopd decides** (`pipeline.ApplyProofChecked`, in one transaction with the usage evaluation):
  - every automatic check passed and nothing left for the user → **verified**, qa → done, actor
    **`loop (proof)`**, words "Proof passed: …" with each check;
  - a command check **failing twice in a row** → **reopened**, the usual reopen (a P2 item in
    triage with the failure as its ask, linked by `reopen_of`; this one done), actor `loop (proof)`. Like the user's reopen, it
    flags the open dependents (#193, `dependency_reopened`).
    One failure only marks it failed and it is checked again 30 minutes later: a flaky check, or a
    deploy in progress, does not file work;
  - otherwise it stays, kind `proof_checked`, with `changed` when its status changed.
  A second report for a proof that is no longer due (two runners, or the user already checked it)
  is `wrong_stage` and not recorded as a refusal.
- **A runner verdict is a new authority**, so the runner never gets the user's routes
  (`/verified`, `/reopen` stay user-only). It reports what it ran; loopd, from the proof the build
  stated and review saw, makes the transition.
- **Pi waits** (state `waiting`) and never verifies an item. When the Pi device lands, its
  checks become `command`-like checks run through the harness broker. Until then such an item
  stays in qa, grouped as waiting. **E2E waits for a regression run** (below).
- **For the loop's own repo** (`qa_after_deploy`) nothing is checked before the deploy is reported;
  usage counts from the deploy event.
- **The user can always verify or reopen by hand** (buttons, `/loop verified`, `/loop reopen`),
  whatever the proof says; that ends the item as before and the proof stays as a record.

## E2E results decide e2e checks (#195)

- **Which tests.** An app item's `e2e` check names the specs and flows that cover the pages and
  screens its PR changed, as jarvis-server's `e2e/coverage.json` (#148) lists them
  (`e2e/web/tests/admin/traces.spec.ts`, `.maestro/schedules.yaml`). The build states them, or the
  sweep does (`skills/build`, `skills/orchestrator`). A change that touches no covered page or
  screen gets a `manual` check whose `look` says why ("touches no covered page: …").
- **Matching** (`pipeline.E2EMatches`): a name matches a run's test when it is the test's
  `suite: title`, its file, or its file with the path from the repo's root in front
  (report.json's web files are relative to `e2e/web`: `tests/x.spec.ts`). Skipped tests do not
  count.
- **When.** In the same transaction as a run's result (`store.RegressionResult`), for each item in
  qa with an e2e check still waiting, not waiting for a deploy, and **merged (or deployed) before
  the run was claimed**: the run checks out main at its start, so a later merge is not in it and
  waits for the next run. The item's repo is not compared with the suite's: the paths are the
  coverage map's.
- **Decided** (`pipeline.ApplyE2EResults`): every name ran and every matching test passed →
  `passed`, evidence "regression R*n* passed: *k* test(s) (/board/regressions/*n*)"; one failed
  (failed, timedOut, interrupted) → `failed`. A name the run did not include (its suite did not
  run, a filter) leaves the check waiting; so does a run that ran only some of its names.
- **A failure reopens at once**, not twice in a row as a command does: the suite retries a test
  itself, and a run is not repeated every 30 minutes, so a second failure could be a day away while
  the item idles its dependents. The reopened item's words are the failing test, its first
  assertion line and the report's link; **its screenshot is the new item's evidence**, and it is
  the item 'File it' shows for that test (`regression_items`), so the run's report has no second
  item to file.
- **Verified** words end with "Regression R*n*: /board/regressions/*n*". A proof with other checks
  still open stays (`proof_checked`, actor `loopd`, `changed` when its status changed); a passed
  e2e check with a manual look left is the user's ask, as for commands. The command checks' 30-minute
  recheck is not moved by a run.
- **Slack:** the item's thread has the usual verified / reopened line by `loop (proof)`; the run's
  report adds "QA from this run's E2E checks: verified #…; reopened #…". The merge message of a
  proof with an e2e check says a regression run failing one of its tests reopens it.
- **Retroactive.** The #194 sweep gave most items already in qa a proof; for an app item that was
  often only a manual check, and the sweep never asks twice. Migration `0027_proof_e2e.sql` marks
  the items in qa then whose proof the **sweep** wrote with **only manual checks**
  (`proof_asked = 2`); the next tick asks the orchestrator once more for each (trigger
  `proof_e2e`, then `proof_asked = 3`). `ApplySetProof` lets a proof replace such a proof (and only
  such: the build's, or one with an automatic check, still refuses a second), recorded as
  `proof_set` with `replaced`. When no test covers the change the orchestrator writes nothing and
  the manual proof stays. Chosen over replacing on every sweep proof: it is one turn's worth of
  triggers, once, for the items the goal names; items reaching qa later get coverage-aware proofs
  from the start.

## The proof sweep (retroactive, and any item without one)

- An item **in qa without a proof** gets **one** orchestrate trigger, `proof_needed`, once per item
  (`items.proof_asked`), at loopd's next tick (`store.OrchTick`). On the first tick after this ships
  that is every item already in the QA column: the retroactive sweep. Later it covers any item that
  reaches qa without a build's proof (built before this, or a build that stated none). Chosen over a
  one-shot flag because it is the same rule for both and cannot miss an item that was mid-land when
  the flag flipped.
- The orchestrator (an orchestrate turn, `skills/orchestrator` "Proofs for items in QA") writes it
  from the item, its PR and its evidence with a new action, **`proof`** (`item_id`, `checks`) →
  `POST /orchestrator/items/{id}/proof` (the orchestrator's token): only on a qa item with no proof;
  a second is refused. Recorded as `proof_set` with its reason; the proof's `by` is `sweep`.
- If the turn writes none, the item stays the user's, as before proofs.
- **Risk:** a proof the sweep writes can verify an item without the user. The skill says never a
  trivial check (`true`, a test that passes without the change); the thread posts the proof as it is
  written, the item's page shows each check with its evidence, and the user can reopen.

## What the user sees

- **Slack, at merge (or deploy):** with automatic checks to run, "#N: Merged — the loop checks it
  itself: usage …; command …", then "Then your check: look at X" if there is a manual one, with the
  Verified / Reopen buttons and **no mention** of the approver. With only manual checks: the usual
  ask with the one line, "<@approver> #N: Merged — waiting for your check: look at X". Without a
  proof: unchanged.
- **Slack, on a check:** posted only when the status changes (checks run every 30 minutes): the
  automatic ones passed and a manual one is left → the ask, "Proof passed — waiting for your check:
  look at X", with the buttons; a first failure → "Proof check failed once, checked again before it
  reopens: …"; only pi/e2e left → "Proof: waits for: …". Verified and reopened by the proof use the
  usual lines with "loop (proof)" as who.
- **The board's QA column** shows the qa items (before this it showed none: no lane read the `qa`
  display), grouped in order: **waiting for a proof** (the deploy, or which checks), **needs you**
  (what to look at; an item without a proof is "no proof: your check"), **failed** (a check that
  failed once). The item page lists the proof's checks with their state and evidence.

## Not done

- No Pi execution (the Pi device). No retry budget beyond "twice in a row" (commands) and one
  failing run (E2E).
- E2E checks wait for a regression run: until runs are started on their own (#152), a qa item
  with an e2e check waits for someone to start one (`@jarvis-loop regression`, the board).
- The real coverage.json → test mapping is the agent's reading (build, sweep); loopd does not read
  coverage.json itself, and a mobile flow's `file` in the real report.json is checked only against
  the format in jarvis-server's docs/dev/e2e.md (`.maestro/x.yaml`).
- `loop show` and `/loop status` do not show the proof (the board and the item's events do).
- The digest still lists every qa item under "Waiting for your check", including ones the loop is
  checking.
