# A proof command runs with the setup's venv; its environment is in the orchestrator's skill

2026-10-22 · item #461. Ten done items' proofs (#4, #5, #9, #10, #11, #164, #165, #186, #187) failed
twice with `/usr/bin/python: No module named pytest` and were reopened, then closed not
reproducible: the tests pass in the repo's venv. The proof's checkout ran the repo's setup (which
makes `.venv`), but the command's `python3` was still the system's. #456's proof cloned into `/tmp`
and the fence refused it (exit 128). Extends [2026-10-19-proof-setup.md](2026-10-19-proof-setup.md).
Enforced by `TestProofCommandUsesTheSetupVenv` and `TestVenvEnv` (`internal/runner/proof_test.go`).

- **When the checkout has a `.venv/bin` after setup, a proof command runs with it active**:
  `VIRTUAL_ENV=<checkout>/.venv` and its `bin` first on `PATH` (`venvEnv`, appended after the
  runner's own so they win). Verify steps get the same for the build's worktree. The runner does
  not build venvs itself: the repo's `setup` in runner.json already does
  ([2026-10-15-all-repos.md](2026-10-15-all-repos.md)); a repo whose setup makes none is a config
  matter, and its proofs build their own (below).
- **The orchestrator's skill says what a command check gets** (`command` kind): a fresh checkout of
  main after prepare and setup; the setup's venv on PATH, or build one in the checkout when there
  is none; writable are the checkout, `$TMPDIR`, `$LOOP_EVIDENCE_DIR` and the toolchain caches,
  never `/tmp` (a private tmpfs under bubblewrap, but read-only under sandbox-exec on the mac
  runners); the network is open but carries no credentials, so no private clone.
- The ten affected proofs were already rewritten by hand to build their own `.venv`; no item data
  changes.
