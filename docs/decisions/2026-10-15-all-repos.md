# Every active repo (phase 6b)

2026-10-15 · phase 6b (`docs/phases/06b-all-repos.md`), the loop side. The repo-side changes (CI and
CLAUDE.md in the docs, the packages, the mobile apps and the installer) and jarvis-server's
mobile-shot changes are other PRs. Each choice below is enforced by a test or a scenario unless it
says otherwise. **Not yet run with a real agent or against real GitHub**: the rollout is the main
session's, after the user's "merge it".

## The user's decisions (2026-10-15)

1. **Mobile ships every merge.** jarvis-node-mobile keeps its push-to-main TestFlight / Play
   internal submission (the testers are the household). Its release config stays on the hold list.
2. **Add PR CI first** where there is none (jarvis-docs, all packages); the land gate keeps
   requiring CI. Those PRs touch `.github/` and are held for one batch approval.
3. **The harness runs on the dev box, run by the runner** ("this computer is typically on 24/7 and
   everything for the harness is already set up"). Of the three options in
   `2026-10-15-runner-choices.md`, option 3: **the runner runs per-repo verify steps after the build
   agent, outside the agent's sandbox.** The agent cannot skip or fake them; the review agent judges
   their output.
4. **Packages: tagging and Pantry submission stay human.** The loop merges code only; a package's
   version, secrets, packages, apt_packages and post_install (its `jarvis_package.yaml`) are held.

## loopd

- **`routed`** (triage → triage): `repo` (a configured slug, only when the item has none, the same
  check as `reproduced`'s repo, now one function) and `why` are required; no evidence (a routing run
  reads one file). The lease ends and the item waits in triage for the next claim. Routing can
  happen once per item: after it the item has a repo. Thread line: "Triage: this is
  `owner/name` — why. Triaging it there next."
- **`verify_failed`** (build → build): the runner's verify failed. `reason` and one evidence file
  (the step's log) are required. It **shares the bounce count** with review's `bounce`: the second
  of either sends the item to the user (needs-you, returning to build).
- **Review's `approved` takes `needs_review: true`**: loopd raises the item to hold ("review: marked
  needs review"), so land waits for the user. The review result schema did not allow it before; it
  does now. This is how content a path rule cannot see is held (a `curl … | sh` pin in a docs page,
  a new `JarvisSecret` in a package): the review skill says when to set it.
- **`--repos-file`**: one `owner/name` per line, optionally `: alias, alias`, `#` comments; added to
  `--repos`. An alias names one repo only and is never another repo's name (refused at start-up).
  loopd's Slack bot gets the aliases; the runner's config has its own `aliases` (shown to triage).
  Two lists to keep in step, as `--repos` already was: loopd cannot read the runner's config (it
  holds the runner's token and lives on another machine from rollout 7).

### Hold rules

- **`HoldRule.repo` may end in `*`**: the rule applies to every repo whose slug starts with the
  rest (`alexberardi/jarvis-cmd-*`), and to a bare name (a runner key) whose name starts so. One `*`,
  only at the end, owner literal (`alexberardi/*` is allowed: every repo of the owner).
- **The new defaults are the spec's lists**, per repo: both mobile apps, jarvis-docs,
  jarvis-installer, and the two package prefixes, each with `ci` (`.github/**`) and **deleted or
  renamed tests**: TypeScript `**/__tests__/**`, `**/*.test.ts`, `**/*.test.tsx` (mobile,
  installer); Python `tests/**`, `**/test_*.py` (docs, packages). Rule names: `release-config`,
  `native`, `store-scripts`, `crypto`, `auth`, `pairing`, `presence`, `config`, `test-config`;
  `well-known`, `hosting`, `deploy`, `site-config`, `security-docs`, `internal-ops`; `secrets`,
  `image-digests`, `service-registry`, `domain`, `scripts`; `package-manifest`, `package-scripts`,
  `package-shared`.
- **One addition to the spec's globs:** `src/services/*Presence*` next to `*presence*`. Globs are
  case-sensitive and the mobile app's services are camelCase (`nodePresenceService.ts` would not
  match `*presence*`). Not checked against the real repo (its checkout was not read).
- **Found and fixed: the built-in rules froze.** Any control change (the active-agents number from
  Slack, a stop) wrote the whole default list into the database as if the user had set it, so new
  defaults never reached a loopd that had ever been throttled. Now a control change keeps the rules
  on the live defaults unless the change sets rules, and **on start-up loopd resets a stored list
  that is exactly an earlier built-in set** (jarvis-server's eight, or phase 6's server + loop list)
  to the live defaults (`pipeline.IsBuiltInHoldRuleSet`). A list the user edited stays theirs. The
  live loopd most likely holds such a copy today; without this, phase 6b's hold rules would not
  apply there.

## Runner

### Config (`runner.json`, per repo)

- `group` (`server`, `loop`, `mobile`, `docs`, `installer`, `package`): shown to triage and in the
  build and review briefs. Hold rules stay keyed by slug in loopd (the runner's group is not
  something loopd should trust).
- `aliases`: shown to triage in `repos.md`; `Config.Repo` also finds a repo by an alias. Unique
  across repos and never another repo's key or slug (refused at load).
- `setup`: commands the runner runs in the checkout **after** `prepare`, before the agent, outside
  the sandbox, output in the run dir's `setup.log`, 20 minutes each; a failure fails the run
  (needs-you) with the end of its output. The mirror's `info/exclude` now also lists `.venv/` and
  `node_modules/` (rewritten on every refresh, so existing mirrors get it), so installed dependencies
  never make the worktree dirty and are never committed.
- `verify`: a list of `{name, run, repo?, timeout?, when_changed?}` (below).
- `verify_lock` (runner level): the lock file, default `~/.cache/jarvis-loop/verify.lock`.

### Triage with many repos: route first

- **An item with no repo gets no checkouts**, only `repos.md` and `open-items.md`. `repos.md` then
  has, per repo: key, slug, group, aliases, description and the **last 5 merged PR titles**,
  fetched 6 at a time within 20 s for all repos; a repo whose titles could not be fetched says so in
  its row and in the brief ("Not available this run"). No `merged-prs-<key>.md` files.
- The brief says "Route it" and the result contract offers `routed` `{repo, why}`; `reproduced`
  with `repo` is still accepted (rare: when that file alone settles it). The runner checks `repo`
  against its config (key, slug or alias) and reports the slug; loopd checks it again.
- The static part of the triage brief is the same for routing and normal runs (one cache prefix);
  the routing text is in the item part. The skill gained a "Routing" section.
- Two runs of one stage within a second (a routed item triaged again at once) used to share a run
  dir; the second now gets a `-2` suffix, so both logs are kept.

### The verify step

After the build agent's `ready_for_pr` passed the runner's git checks and before anything is pushed:

- **Only the runner's config**: the steps are `runner.json`'s, never the agent's or the PR's. The
  result schema has no field for commands (unknown fields are refused) and nothing in `.loop/` is
  run (scenario `verify-not-the-agents`).
- **A change to a file the runner trusts is not verified with the agent's version of it**: if a
  changed path (or a rename's old path) is one of the repo's `deny_write` paths, under one, or
  matches one as a glob, verify does not run and the run fails to the user. The guard already
  refuses the agent's edits there; this catches a shell command that slipped past it. The spec's
  "add `scripts/mobile-shot`, `scripts/sandbox`, `scripts/screenshots` to jarvis-server's
  `deny_write`" is a runner.json change (example below), not code.
- **Each step**: `bash -c run`, as the runner, in its own process group, cwd the worktree or, with
  `repo`, a fresh detached checkout of that configured repo at its base (removed afterwards), with
  `LOOP_ITEM`, `LOOP_HEAD`, `LOOP_WORKTREE`, `LOOP_EVIDENCE_DIR` (a fresh dir in the run dir, outside
  the worktree), and beyond the spec `LOOP_SANDBOX` (`loop-<id>`), `LOOP_REPO`, `LOOP_BASE` and
  `LOOP_MIRROR` (the runner's bare mirror of the item's repo: mobile-shot's `JARVIS_MOBILE_REPO`).
  The environment is the agent's (no loopd or Slack secrets). `when_changed` globs skip a step when
  no changed path matches. Steps run in order and stop at the first failure.
- **Time**: a step's `timeout` (default 20 m), cut to what is left of loopd's per-run cap minus a
  minute; heartbeats keep the lease while it runs. A timeout is a failed step (back to build); a step
  cut short by the run's cap is the runner's failure (needs-you). The SIGTERM-then-SIGKILL of the
  group cannot reach a harness started with `setsid` (jarvis-server's `scripts/sandbox up`): the
  step's own command must take it down (a `trap`, below).
- **Evidence**: the step's log tail (80 lines, 16 KB) as `verify-<n>-<step>.log` and every regular
  file it wrote to `LOOP_EVIDENCE_DIR` (images included; at most 20, 20 MB each, as for the agent)
  as `verify-<n>-<step>-<file>`, labelled `runner verify "<step>": …`. The review agent gets them
  with the rest of the item's evidence, and its skill says to judge them.
- **Pass**: the runner pushes, opens or updates the PR, and the Verification footer lists the
  runner's steps first, under **Runner verify**, apart from the agent's evidence files (land's
  trailer check is unchanged).
- **Fail**: nothing is pushed and no PR is opened or updated; the log and evidence are uploaded and
  the runner reports `verify_failed` with `reason` (one line: the step and its result), and the log
  tail in a separate field. **The log never goes to Slack**: the thread says only which step
  failed. The next build continues the branch from the mirror and gets `.loop/review/verify.md`
  (each failure, its commit and the end of its output); its brief says it was sent back by verify.
- **Stop or shutdown during verify**: the step is ended and nothing is reported or pushed; the
  commits stay in the mirror and the next run resumes them.
- **One verify per machine**: an exclusive `flock` on `verify_lock`, waited for with heartbeats (at
  most 30 minutes, then the runner's failure). A lock is per open file, so two slots of one runner
  exclude each other as two runners do. The harness and the tests use their own lock file.

### The fence (review finding, 2026-10-15)

`setup`, `prepare`, `cleanup` and `verify` commands run the agent's code (npm scripts, tests, a
jarvisd built from the PR) outside the agent's OS sandbox, where the user's HOME is visible. They
now run under **bubblewrap** (`fence.go`):

- `bwrap --dev-bind / / --unshare-pid --proc /proc --die-with-parent --new-session`: the host's
  filesystem and **network namespace as they are** (loopback is needed by the sandbox jarvisd, the
  emulator and the LLM tap; no `--unshare-net`). A private pid namespace so everything a step
  started ends with it (`--new-session` takes it out of the runner's process group, which is how
  steps were stopped before).
- **Masked** (`verify_mask`, runner config; missing paths skipped): a directory gets a `--tmpfs`, a
  file `--ro-bind /dev/null`. Defaults: `~/.ssh`, `~/.config/gh` (a GitHub token with push rights
  to every repo), `~/.config/jarvis-loop` (loopd tokens), `~/.config/jarvis-harness/slack.env`,
  `~/.local/share/jarvis-loop` (loopd data), `~/.gnupg`, `~/.netrc`, `~/.git-credentials`,
  `~/.config/git/credentials`, `~/.docker/config.json`, plus always the runner's own config file
  and its `loopd_tokens_file` / `loopd_data_dir`.
- **Accepted exposure:** `~/.config/jarvis-harness/installed.env` stays readable: jarvis-server's
  sandbox needs it for the LLM tap, and it is an app client for the local jarvisd only (it can use
  the installed jarvisd's LLM API, not GitHub, Slack or loopd).
- **Environment:** on top of the agent's scrub (loopd, Slack), drop `GH_TOKEN`, `GITHUB_TOKEN`,
  `GH_ENTERPRISE_TOKEN`, `GIT_ASKPASS`, `SSH_ASKPASS`, `SSH_AUTH_SOCK`, every `GIT_CONFIG_*`, and
  every `*_TOKEN`, `*_KEY` and `*_SECRET`. No allowlist: no setup or verify step needs one of the
  user's secrets (the harness reads its own from installed.env).
- **No pushing:** `GIT_CONFIG_GLOBAL` is a runner-written file with an identity, an empty
  credential helper, no signing and no hooks; `GIT_CONFIG_NOSYSTEM=1`; `GIT_TERMINAL_PROMPT=0`.
  With `~/.config/gh` and the credential files masked there is no login left to push with.
- **Fail closed:** the runner probes bubblewrap once (loop-runner at start, logged); if it is
  missing or cannot start, setup, prepare, cleanup and verify refuse to run, the item goes to the
  user with the reason, and nothing is pushed. Never a fallback to unfenced.
- Tests: `TestFenceHidesSecrets` (a fake HOME with the credential files: a setup and a verify step
  that read them, list `~/.ssh` and print the tokens get nothing; installed.env readable; a
  loopback HTTP server answers; no credential helper), `TestFencedEnv`, `TestFenceFailsClosed`,
  `TestDefaultVerifyMask`. CI installs bubblewrap and allows unprivileged user namespaces. No
  scenario: one would have to read the real user's files to prove they are hidden.
- Not fenced: the runner's own git and gh calls (they need the login) and the agent itself (its own
  sandbox).

## Slack repo words

- **Aliases** (loopd's `--repos-file`) count only as a leading `[x]` or `x:`, or a trailing `in x`
  (nothing after it but punctuation and priority words: "… in recipes app, high priority"). Never in
  the middle of a sentence ("make the mobile layout denser" stays without a repo, for routing).
- **A repo's short name** (its name without `jarvis-cmd-`, `jarvis-device-` or `jarvis-`: `nest`,
  `docs`, `server`) is an alias too when only one repo has it, but **only as a leading `[x]` or
  `x:`**, not `in x`: package names are ordinary words (`timer`, `weather`), and "fix the rounding in
  timer" more likely means jarvis-server. A configured alias wins over a derived one; a full name or
  slug wins over both and keeps its old forms (`in jarvis-server` anywhere).
- Matching is case-insensitive and multi-word aliases match any whitespace. Table:
  `TestParseRepoAliases`; scenario `repo-alias`.

## Risks

- **Verify and setup run the agent's code outside the agent's sandbox**: tests, `npm` lifecycle
  scripts, a package's `jdt test`. That is option 3 as chosen. The fence hides the credentials and
  stops pushes, but the code still runs as the user with the rest of HOME writable and the network
  open (it could, say, damage other checkouts or call out). The deny_write check keeps the harness
  scripts themselves trusted.
- A long build plus a long verify can reach loopd's 45-minute cap; verify is cut to fit and fails to
  the user rather than overtime, but such items will need the cap raised.
- The hold rules reset on start-up assumes a stored list equal to a built-in set was not chosen on
  purpose; the effect is only that later defaults apply to it.
