# The test Pi: targeted SSH through the harness broker

2026-10-18 · the user's decision (was loop item #183, built in an interactive session because it
moves the agents' own boundary). The Go Pi node items (jarvis-server #157–#181) can only be
verified on a real Pi: the HAT's audio, LEDs and button, the install on the device, the
provisioning hotspot. The lab Pi exists only for testing, so the user chose to give build agents a
real shell on it ("targeted SSH") rather than a fixed set of verbs.

## What changes

- **A `pi` resource** (`pipeline.Resources`, a limit key, loopd's limit 1 from migration 0019).
  Triage marks an item that needs the Pi; only a runner with the `pi` capability claims it, one
  at a time.
- **The runner's `pi` block** (`runner.json`): `host`, `user`, `port` (22), `key`, `known_hosts`,
  `restore`, `timeout` (20m). The key is the loop's own (never the user's `~/.ssh` key, which
  reaches other machines); it and `known_hosts` must exist, the key mode 0600, and both join the
  secrets every agent and verify step is denied. `restore` is what puts the Pi back as the user
  keeps it (on the lab Pi 4: `sudo systemctl start jarvis-node`). A `pi` capability without the
  block, or the block without the capability, is a config error.
- **Three broker ops** (`loop-harness pi '<command>'`, `pi-put <file> <path>`, `pi-get <path>
  <file>`), for build and review runs of an item that needs the Pi, on a runner that has one. A
  repo needs no harness for them; a Pi-only session refuses `up`, `run` and `down`.
  - The runner, outside the agent's sandbox, runs `ssh` itself: `-F /dev/null` (no config
    file), only the loop's key (`IdentitiesOnly`, `IdentityAgent=none`), `BatchMode`, the pinned
    host key (`StrictHostKeyChecking=yes`, its own `known_hosts`, no global one), no forwarding
    of any kind (`ClearAllForwardings`, `ForwardAgent=no`, `ForwardX11=no`), no local command,
    the host after `--`. The environment is the fenced one (no agent socket, no askpass). The
    agent names no host, user, key or option.
  - **What runs on the Pi is not limited.** That is the point: the agent stops the Python node,
    installs, reboots, reads logs. The guard still refuses protected words in a `pi` command
    (the user's emulator, the protected paths), as for any command.
  - Every command runs in the item's own scratch dir, `~/loop-scratch/<item>`. `pi-put` reads
    only a plain file inside the worktree (through an `os.Root`: no `..`, no symlink out), and
    writes only under the scratch dir; `pi-get` the other way round, written to a temp name and
    renamed, removed on failure. Paths on the Pi must be relative with no `..`.
- **One item at a time, and the Pi put back.** The broker holds the Pi for the first session
  that uses it and refuses others ("in use by item #N") until it ends, besides loopd's limit.
  Before an item's first command the runner removes every scratch dir (a crashed runner's too)
  and runs `restore`; when the item's run ends (exit, time cap, lease lost, runner shutdown) it
  removes the item's scratch dir and runs `restore` again. A session that never used the Pi
  touches nothing.
- **The agent's own `ssh`, `scp` and `sftp` stay denied** (deny rules, guard), so this supersedes
  only the "no remote shells" part of `2026-10-15-runner-choices.md` for the Pi, through the
  runner. The brief's "This run" part explains the three ops when the item has the Pi.

## Not chosen

- **Opening `ssh` to the agent** (an allowed alias in the guard, the Pi's port on the sandbox's
  network allowlist, the key readable in the sandbox): the key would be the agent's to copy, and
  `ssh` has many ways to reach elsewhere (`ProxyJump`, `ProxyCommand`, `-o`, forwarding, config
  includes) that a guard would have to keep up with. Through the broker the agent never holds the
  key and never builds the command line.
- **Fixed verbs only** (deploy, run for N seconds, collect metrics): safe, but every new kind of
  check would wait for a loop change, and the Pi is a test device.

## Setup (the user, once)

1. A key for the loop: `ssh-keygen -t ed25519 -N '' -C jarvis-loop-pi -f ~/.config/jarvis-loop/pi/id_ed25519`.
2. On the Pi, append `~/.config/jarvis-loop/pi/id_ed25519.pub` to the user's
   `~/.ssh/authorized_keys`, optionally prefixed `from="<the runner's address>"`.
3. Pin its host key: `ssh-keyscan -t ed25519 <host> > ~/.config/jarvis-loop/pi/known_hosts`
   (and compare the fingerprint with the Pi's own `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`).
4. `runner.json`: add `"pi"` to `capabilities` and the block, then restart `loop-runner`:
   `"pi": {"host": "<host>", "user": "pi", "key": "~/.config/jarvis-loop/pi/id_ed25519",
   "known_hosts": "~/.config/jarvis-loop/pi/known_hosts", "restore": "sudo systemctl start jarvis-node"}`.

## Tests

`internal/runner/pi_test.go`: the exact ssh command line; the config's refusals (an option as
host, two hosts, a bad user, a readable key, no key or known_hosts, no restore, a bad timeout or
port, the capability without the block); a session end to end over a fake ssh (preparation once,
a crashed run's scratch removed, commands in the scratch dir, put and get, a failed get leaving
nothing, paths out of the scratch dir or the worktree refused, a symlink out of the worktree
refused, restore and release at the end, no agent socket reaching ssh); one item at a time; the
ops only for items with the resource; the brief, the deny rule and the guard. Scenario
`66-pi-resource`: only a runner with `pi` claims the items, one at a time.
